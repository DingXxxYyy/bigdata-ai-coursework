Skill（Agent Skill）

在 AI Agent 语境里，"Skill" 不是游戏里的技能，而是"教 Agent 特定专长的一套可复用文件"。它为何重要？和 Plugin / MCP / Tool 有何区别？如何动手做一个？本文用 7 章节讲透。

学科：人工智能 / Agent 工程 深度：系统掌握 + 应用导向 受众：零基础愿意投入（可动手做） 语言：中文

1个人解释（用自己的话）

先一句话 + 一个比方建立直觉。

一句话本质

Skill = 一个包含 SKILL.md 指令文件（可再加脚本/参考/资源）的文件夹，让 Agent 在需要时按需加载，从而获得某项"特定专长"。它本质上是"打包好的专业知识与流程"，能被通用 Agent 发现、加载、执行。

生活化比方

把一个 Skill 想成给新员工的一本 onboarding 手册 + 配套工具：手册（SKILL.md）写明"遇到这类任务你该怎么一步步做、注意什么"，必要时还附带现成脚本、规范文档、模板。平时只放目录里不占地方，当任务对口时，员工（Agent）才翻开对应那本手册照着干。官方原话："给 Agent 建 Skill，就像给新员工整理入职指南"。

30 秒教外行版

"想让 AI 助手特别擅长某件事（比如做表格、整理公司格式的文档），不用每次把'该怎么做'的规则重复讲一遍。你把这些规则和工具打包成一个文件夹（叫 Skill），AI 遇到这类活时自己会去读它照着做——省事、规范、还能跨项目/跨人复用。"

关联锚点

如果已理解本系列前两篇：Agent 决定"要不要做、怎么做"（自主循环），Skill 提供"做某项专长的具体知识与流程"（能力封装），而 MCP 提供"连外部数据/工具的标准接口"——三者是不同层面，可组合使用。很多通用 Agent（如 Claude、本工作区的 WorkBuddy）都用这种"按需渐进加载"来扩展能力。

2核心机制（How it works）

核心是"目录结构 + 元数据触发 + 渐进式按需加载"。

一个 Skill 长什么样（目录结构）

my-skill/                    # 一个 Skill = 一个文件夹
├── SKILL.md                 # 必需：元数据 + 指令主体
├── scripts/                 # 可选：可直接执行的可复用代码
├── references/              # 可选：按需加载的参考资料
├── assets/                  # 可选：输出时用到的模板/资源
└── ...其他文件               # 官方规范允许任意补充文件

SKILL.md 的 YAML 元数据（触发入口）

SKILL.md 必须以 YAML frontmatter 开头，至少含两个字段：

---
name: pdf
description: Fill PDF forms, read/analyze PDFs, and extract form fields. Use this when…
---
# 下面是给 Agent 的分步指令（正文）
字段约束（以官方文档为准的示例）：name 仅限小写字母/数字/连字符、≤64 字符、不能含保留词（如 anthropic、claude）；description 非空、通常 ≤1024 字符，必须同时说明"它做什么 + 何时用"，因为 Agent 靠 description 判断何时触发本 Skill。

渐进式按需加载（Progressive Disclosure）——核心设计

层级何时加载内容
① 元数据启动时（常驻）每个 Skill 的 name + description 进系统提示，让 Agent 知道"有哪些可用、何时该用"，开销很小
② SKILL.md 正文任务匹配到该 Skill 时Agent 读入完整指令开始执行
③ 关联文件/脚本执行中需要时才读/执行references、scripts 等，按需发现，不一次性占上下文

好处：Agent 可装大量 Skill，但只在任务需要时才真正把指令读进上下文，省窗口、够灵活。脚本还能不读内容直接运行（适合确定性操作）。

一个触发时刻（走查）

  1. 用户发来任务 → Agent 的系统提示里已带各 Skill 的 name/description。
  2. Agent 判断该任务匹配某 Skill 的 description → 用工具读取该 Skill 的 SKILL.md。
  3. 正文若引用 bundled 文件（如 forms.md）→ 需要时再读取。
  4. Agent 按指令完成任务，甚至执行 Skill 附带的脚本。

代码直觉（最小 Skill 的样子）

# 一个最简 Skill 目录示意（实际就是文件）
my-date-helper/
└── SKILL.md
---
# content of SKILL.md
---
name: date-helper
description: 用一致格式格式化日期。当用户要求按"YYYY-MM-DD"输出日期时使用。
# ---（真实文件里 frontmatter 需闭合）---

## 指令
当任务要求格式化日期时：
1. 统一转为 YYYY-MM-DD。
2. 若输入含时区歧义，向用户确认后再转换。

注：上面为直观教学演示，真实 SKILL.md 必须用规范写法与闭合的 YAML frontmatter；具体格式以你所用平台的 Skill 规范文档为准。

3应用场景（When / Where to use）

Skill 的用武之地是"反复出现的、需要特定专长或流程"的任务。

典型落地场景

  • 垂类文档能力：如做 Excel/PPT/Word/PDF——把"格式规范 + 处理脚本"打包成 Skill，让 Agent 直接产出专业文件。
    适合：任务类型固定、有明确模板与步骤。
  • 组织/个人规范内化：品牌指南、报告格式、代码规范——把"自家怎么写"的规则沉淀成 Skill，跨人跨团队复用。
    适合：可复现、需一致的流程。
  • 专业领域专家流程：法律审阅、数据分析 pipeline、演示排版——把专业判断的步骤文档化。
    适合：模型欠缺的程序性知识，Skill 来补齐。
  • 作为"给 Agent 的上岗培训"：让通用 Agent 在特定任务上表现得像"专才"，而不必为每个场景单独造定制 Agent。
    适合：想用"可组合能力"而非"碎片化特制 Agent"。

一条关键提醒

Skill 给了 Agent 执行代码/调工具的能力，等于"装软件"——必须只用可信来源。恶意 Skill 可能诱导 Agent 越权调用工具、外泄数据。使用非官方 Skill 前务必审阅其全部文件（SKILL.md、脚本、图片等），警惕"行为与描述不符"的异常。

4边界辨析（Limits & 易混辨析）

Skill 常和 Plugin / Tool / MCP / Workflow 混在一起，必须分清。

Skill vs 相邻概念

对比维度SkillTool / MCPPluginWorkflow
本质文件夹 + 指令/资源（教"怎么做"）可调用的功能/数据接口（"能做什么"）产品生态的扩展单元（各家定义略不同）预设的固定流程编排
侧重专业知识与流程封装执行动作/取数据分发与集成的载体流程控制权在代码
加载方式按描述渐进加载指令声明接口供模型调用安装后对应用/Agent 生效固定顺序执行
与 Agent 关系给 Agent"补专长"给 Agent"补手脚/信息源"把能力打包分发给 Agent/应用给 Agent 定"套路"

一句话记忆：Skill 回答"这项专业活怎么做"，Tool/MCP 回答"怎么连外部世界"，Workflow 回答"整套流程怎么排"，Plugin 更像"能分发的整合包"。它们常一起用，但概念不是一回事。

常被误用的负面场景

  • 把 Skill 当成能"凭空变出能力"的魔法——它只提供指令/脚本，无法绕过底层模型的能力上限。
  • 在 SKILL.md 里堆大量不相关、或用不到就加载的巨型内容——违背"渐进加载"，白白耗上下文；应把细节拆到 references，按需读取。
  • 从不审阅就直接启用第三方 Skill——存在数据外泄/越权风险。
  • 把 Skill 与 Tool/MCP/Workflow 混为一谈去选型——会选错架构。

6学习路径（进阶建议）

边做边学，最容易上手——毕竟 Skill 本身就是"结构化文件"，门槛不高。

  1. 前置知识：了解 Agent、Workflow、MCP/Tool 的边界（见本系列其他篇）；知道 YAML frontmatter 基本语法。
  2. 入门（第 1 步）：通读官方《Agent Skills》文档 + 《Introducing Agent Skills》，先搞懂"什么是 Skill、何时触发、SKILL.md 字段要求"。
  3. 建立心智模型：读懂"渐进式按需加载"三级结构，理解为什么 SKILL.md 要写得精炼、细节进 references。
  4. 上手（小实践）：亲手做一个最简单的自定义 Skill（如"统一日期格式"），在自己的 Agent/工具里触发它跑通全流程。
  5. 深入：做一个带 scripts + references 的较复杂 Skill（如文档排版/数据 pipeline），学习"哪些用指令、哪些写脚本"的取舍与评测方法（用代表任务评估改进）。
  6. 产出：把一个你自己反复用、很繁琐的多步流程沉淀成可分享的 Skill 并写清 description，让别人/别的项目也能一键复用。

7自测与常见误区

能答对下面几题，才说明你真的"会"了，而不只是"听过"。

① 一个 Skill 的"必需文件"和"必需字段"分别是什么？

答案：必需文件是 SKILL.md；其 YAML frontmatter 至少含 name 与 description 两个必需字段。scripts/references/assets 均可选。

② 为什么 SKILL.md 的 description 要写"做什么 + 何时用"？

答案：因为 Agent 主要靠 description 来判断某任务是否匹配本 Skill 并决定是否触发；写得不清晰会导致"该触发时不触发"或"乱触发"。

③ 渐进式按需加载（Progressive Disclosure）解决什么问题？

答案：避免把所有 Skill 的完整指令一次性塞进上下文。只常驻 name+description，任务匹配才读 SKILL.md，需要时才读关联文件/跑脚本——从而省窗口、能装大量 Skill、够灵活。

④ Skill 与 MCP/Tool 的本质区别是什么？

答案：Skill 侧重"封装某类专业活的指令与流程（怎么做）"；MCP/Tool 侧重"提供可调用的功能或外部数据接口（能做什么）"。二者互补可组合。

⑤ 使用第三方 Skill 前最该注意什么？

答案：安全。把它当"装软件"看待：只用可信来源；非官方 Skill 务必逐文件审阅（SKILL.md/脚本/资源），警惕会诱导越权调用工具、外泄数据的异常行为。

⑥ 判断题：SKILL.md 内容越多、越详细，这个 Skill 就越好。

答案：错。违背渐进加载原则——无关或低价值的巨型内容会在不该触发时仍占上下文。应把 SKILL.md 保持精简，细节拆到 references 按需读取。

新手最容易犯的 4 个错误

  1. description 只写"它是什么"而不写"何时用"，导致触发不准。
  2. 把 Skill 与 Tool/MCP/Workflow/Plugin 混为一谈去选型。
  3. SKILL.md 一股脑塞大量内容，不利用渐进加载拆 references。
  4. 不审阅就启用第三方 Skill，忽略数据安全与越权风险。
