Agent（智能体）

在 AI 语境下，"Agent" 到底指什么？它与"工作流(Workflow)"有何区别？本文按 7 章节带你把一个概念从"会背定义"学到"能辨别、能使用、能自查"。

学科：人工智能 / 智能体系统 深度：系统掌握 + 应用导向 受众：零基础愿意投入 语言：中文

1个人解释（用自己的话）

先不背定义，先建立直觉。

一句话本质

Agent = 一个能"看情况自己拿主意去做事"的 AI 系统——它不再只是回答你问题，而是为达成某个目标，主动决定"下一步做什么、调不调用工具、要不要改计划"，并循环执行直到完成。

生活化比方

把 Agent 想成一位弹性很大的主厨：顾客只说"今晚来客人，你看着办"。主厨自己决定逛几个菜场、买什么菜、做几道菜，途中发现缺一味调料还会临时调整，甚至打电话问客人忌口。相比之下，"工作流(Workflow)"更像中央厨房的 SOP：洗菜→切丁→下锅，路线是事先画死的，模型只是某些环节里的一双"巧手"。（这个比方参考业界流传最广的解读方式）

30 秒教外行版

"普通聊天 AI 你问一句它答一句；Agent 是你给它一个目标，它会自己拆步骤、自己查资料、自己调工具、自己检查做完没有，一步步干完再向你交差——中间不用你一直盯着指挥。"

关联锚点（帮你记住）

如果你已了解"ChatGPT/大模型"，那么：大模型是"大脑"，Agent 是"大脑＋身体＋自主性"的完整系统。大脑负责思考，Agent 额外拥有"动手能力（工具）""记事能力（记忆）""自己定路线（规划）"——这也是一个概念体系里 Agent、Workflow、Tool 各自位置的起点。

2核心机制（How it works）

业界对 Agent 的组件划分高度一致，核心是"感知→决策→行动→再观察"的循环。

一个反复出现的架构共识

被广泛引用的 Lilian Weng 综述（OpenAI 应用研究负责人）提出，一个 LLM 驱动的自主 Agent 系统里，LLM 当"大脑"，配三个支柱：

  • 规划 Planning——任务分解（把大目标拆成子目标）、反思改进（回顾自己做错什么、调整后续）。典型技术：思维链 CoT、ReAct（思考↔行动交替）、Reflexion（自我批评后重来）。
  • 记忆 Memory——短期记忆≈上下文窗口内的即时学习；长期记忆≈外部向量库＋检索，让 Agent 跨长时间记住东西。
  • 工具使用 Tool use——调用外部 API/代码/搜索，拿到模型训练时没有的信息，突破"只会凭记忆生成"的局限。
另一个通用表述：现代资料常把 Agent 拆成 5 大支柱——基础模型(Foundation Model) / 记忆(Memory) / 规划(Planning) / 工具使用(Tool Use) / 行动执行(Action Execution)。无论 3 支柱还是 5 支柱，思路一致：模型负责思考，周围配齐"记忆＋工具＋规划＋执行"。

关键区别：Workflow vs Agent（谁掌握控制权）

Anthropic 的官方工程博客给出的判据最实用：把这类系统统称 agentic systems，再按流程控制权在代码还是在模型切两类：

维度Workflow（工作流）Agent（自主智能体）
流程控制权在代码，路径预先写死在 LLM，模型动态决定下一步
是否用工具可调用，但顺序固定按当前状态自主选择工具与顺序
典型优点稳定、可复现、易调试、成本可控灵活、能处理开放/未知任务
典型代价难以应对变化场景延迟高、Token 贵、可能无效循环、难排障
生活比方有轨列车（轨道铺好）自动驾驶（按路况动态调）

Agent 循环（一次任务的运转过程）

  1. 接收目标：得到用户目标与可用的工具/权限边界。
  2. 观察：读取当前任务状态、用户请求、记忆里的相关信息。
  3. 决策：由 LLM 判断下一步——回答、调工具、改计划、还是结束。
  4. 行动：执行所选动作（调 API、跑代码、搜网页等），得到新结果。
  5. 再观察→循环：把执行结果写回任务状态，再次进入"决策"，直到目标完成或需要人介入。
是否"必须"有规划模块？不一定。简单任务可"走一步看一步"，逐个决策即可；复杂任务才值得先分解再执行。判断是不是真 Agent 的标准是：它能否根据中间结果动态改变下一步，而不是照固定脚本走到底。

最小代码直觉（骨架示意）

# 伪代码：理解 Agent 的核心是"决策循环"，而非某个神秘框架
goal = "帮用户查某公司最新季报并总结"
state = {"goal": goal, "history": [], "done": False}

while not state["done"]:
    action = llm_choose_action(state)   # LLM 决定下一步（含用哪个工具）
    if action == "search":              # 工具调用
        result = search_tool(state["query"])
        state["history"].append(result) # 观察结果并回写
    elif action == "finish":
        state["done"] = True
# 提示：真实工程用 API 直连 + 函数调用(function calling)即可起步，
# 多数模式几行代码就能实现，不一定要上重型框架。

3应用场景（When / Where to use）

Agent 不是万能的，下列场景才真正需要它的"自主决策"。

典型落地场景

  • 多文件代码开发 / 修 Bug：任务跨很多文件、每步改动面不一，需要读文件→查上下文→改代码→跑测试的自主闭环。
    为什么适合：步骤数事先说不清，要靠模型临场决策。这也是 SWE-bench 类 Agent 的主流用法。
  • 对话式客服 + 业务动作：既要闲聊、又要查库、改工单、触发退款，需要"聊＋做"结合、且能从工具结果拿到强反馈。
    为什么适合：信息源不可预知，动作多，反馈明确。
  • 多源检索后的综合研究 / 报告：从多个外部系统或网页抓取再整合，Agent 决定何时该再搜一轮、何时收尾。
    为什么适合：评估"要不要继续搜"本身就是开放决策。
  • 需要个性化与持续记忆的个人助手：记住偏好、跨会话延续任务，靠长期记忆把上下文外置。

一条关键提醒（很多人踩坑）

默认答案：越简单越好。Anthropic 反复强调：先用"单次模型调用＋检索＋几个示例"做 baseline，够用就别上 Agent；需要更复杂时，先考虑 Workflow（要稳定一致时），再考虑 Agent（要临场决策时）。盲目追求"全自主 Agent"只会换更高延迟和账单。

4边界辨析（Limits & 易混辨析）

这个概念最容易在"名词混战"里被用错。

易混辨析：三个近邻概念

对比维度AgentWorkflow单次 LLM 调用（增强检索）
决策权模型动态决定代码预设一次性生成，无循环
有无循环有（观察→决策→行动）有，但顺序固定无
工具调用自主选、自主排按脚本调用通常无/简单注入
复杂度成本最高中最低

常被误用的负面场景

  • 任务边界清晰、步骤可枚举时硬上 Agent——只会更贵更慢更难调试，此时 Workflow 或单次调用更合适。
  • 把"套了 Agent 框架名字"就当 Agent——判断依据是"决策权实际在代码还是在模型"，不是框架的宣传标签（有的框架把 Agent 只实现成固定 DAG，那其实是 Workflow）。
  • 忽略可控性/安全——自主性越高，单步小错可能滚雪球（错误累积）；工具接口写得烂会让模型行为指数级变差；上线前应沙箱测试、设停步条件、明确权限边界。

前提与失效条件

Agent 的价值前提是：成功标准能量化、反馈闭环存在、人机协同有闸口。若目标含糊到连"成功"都难定义，或环境毫无反馈，Agent 容易空转。注意：Agent 概念在 LLM 之前就已存在（传统 AI/机器人学里的自主 agent），这里的讨论特指以 LLM 为核心控制器的现代 LLM Agent，二者别混为一谈。

6学习路径（进阶建议）

从零到"能给别人讲清 + 能做小 Agent"。

  1. 前置知识：了解大模型/Transformer 基本概念、什么是 prompt 与函数调用(function calling)。
  2. 入门（第 1 步）：读 Anthropic《Building effective agents》原文前两节，先搞懂 Workflow vs Agent 与"何时不该上 Agent"。
  3. 建立心智模型：读 Lilian Weng 综述前 3 章，把"规划/记忆/工具"三支柱记牢。
  4. 上手（小实践）：用 LLM API 直连写一个最简单的 ReAct 风格循环（思考→调工具→观察），先不要上重型框架，看真实输入输出。
  5. 深入：复现一个带工具的 Agent（如让它在沙箱里查网页/跑代码），研究记忆外置（向量库/RAG）与工具接口设计（把工具当 Junior 同事的 API 文档写）。
  6. 产出：做一个能端到端完成的真实小任务（如自动整理资料并生成报告），并用 20 条黄金任务做周更回归，重点盯"工具误用率、越权调用、瞎编引用"。

7自测与常见误区

能答对下面几题，才说明你真的"会"了，而不只是"听过"。

① 一句话判断题：给 LLM 接了多个工具，但每一步和调用顺序都事先写死，这是 Agent 吗？

答案：通常不算，更宜叫 Workflow（工作流）。判据是"决策权在代码还是在模型"——顺序写死则流程控制权在代码，属于 agentic system 下的 Workflow 分支。

② Agent 的三支柱（Lilian Weng 框架）是哪三样？

答案：规划(Planning)、记忆(Memory)、工具使用(Tool Use)。有的资料扩充为 5 支柱（再拆出基础模型、行动执行），思想一致。

③ Agent 的"短期记忆"约等于哪个技术概念？

答案：上下文学习 / 上下文窗口内的即时信息。它短暂且受窗口长度限制；长期记忆才对应外部向量库＋检索。

④ 哪个场景最不该用自主 Agent？

答案：任务边界清楚、步骤可完整枚举、要求结果稳定一致时。此时 Workflow 或单次调用更便宜可靠，硬上 Agent 是常见反模式。

⑤ Agent 为什么可能比单次调用更贵、更慢？

答案：因为它多轮循环：每次决策都产生新的推理 token 与上下文，长期对话还要为历史/记忆付费；自主性也可能带来无效循环与错误累积。

⑥ 判断题：Agent 概念是 2023 年才有的大模型专有词。

答案：错。"自主 Agent"在 LLM 之前已存在于传统 AI 与机器人学；本资料讨论的是以 LLM 为核心控制器的现代 LLM Agent，二者概念谱系不同。

新手最容易犯的 4 个错误

  1. 一上来就套重型 Agent 框架，连"需不需要 Agent"都没判断。
  2. 用营销标签而非决策权来判断"是不是 Agent"（框架可能只是把 Workflow 起了个 Agent 名）。
  3. 忽略工具接口质量——把工具写得像谜语，Agent 行为会指数级变差。
  4. 忘记安全与停步条件——不加沙箱、不设最大轮数与权限边界就让 Agent 自主行动。
